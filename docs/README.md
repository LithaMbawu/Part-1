# RaceDay Part 1 Planning

This folder contains the design artifacts required before API implementation:

- `raceday-erd.png`: ERD export showing six entities, keys, cardinalities, and the many-to-many category relationship.
- `raceday-erd.mmd`: Mermaid source for the ERD, retained for future updates.
- `api-endpoint-plan.md`: planned REST API contract for authentication, profiles, events, categories, enrolments, and results.
- `raceday-schema.sql`: SQL Server schema, constraints, and realistic seed data.

## Design decisions

`Users.Role` is a constrained value (`Admin`, `Organiser`, or `Participant`) rather than a separate role entity. This keeps the role-based authorization model explicit while avoiding a role join that is not required by the brief. Passwords are represented by `PasswordHash`; plaintext passwords are never stored.

An event can offer several categories and a category can be offered by several events through `EventCategories`. An enrolment selects one event category, and a result belongs to at most one enrolment through a unique foreign key. This means the SQL script and ERD use the same six entities and relationships.

The seed data uses placeholder BCrypt-style password hashes for documentation purposes. Part 2 must replace these with hashes generated by the API's chosen password-hashing implementation before using the data in a real environment.
